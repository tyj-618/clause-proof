# 工程心得

每条都来自本项目实际踩过的坑。格式统一为：现象 → 规则。

## 1. 一个契约变更就是一次任务

**现象**：`0002` 从 0.2 升到 0.3 时，文档、实现、测试三处需要同步，手工改到第三处时测试挂了。

**规则**：契约变更牵动多处时，写成一个任务书，交给 AI 一次做完；手工只适合一行 typo 的规模。

## 2. 自述不能作为验收依据

**现象**：实现者报告「make check 全绿、73 个测试通过」，但实际有 3 个失败。

**规则**：任何「已完成」的声明，都要用自己跑的命令复核。审 code 时看 `git diff`，不看对话里的描述。

## 3. 断言格式不等于断言内容

**现象**：错误信息渲染出了错误的实际值，但测试用 `message.startswith("models: X 违反 ")` 断言，格式对，内容错，测试全绿。

**规则**：断言要覆盖「对外可见的每一个部分」。格式和内容分别断言。

## 4. 必填字段比可选字段更能暴露错位

**现象**：两个字段被加错了类（加到了 `CallMeta` 而不是 `RunMeta`），因为它们是必填的，3 个测试立刻变红。

**规则**：契约里不要给默认值。默认值会把错位的字段静默吞掉。

## 5. 生成物不等于该忽略

**现象**：`uv.lock` 是工具生成的，但漏提交它，别人装到的依赖版本就不同，评测数字失去可比性。

**规则**：判据是「别人 clone 后能否重建出**相同**结果」。能重建且与他人无关 → 忽略；能重建但决定版本 → 提交。

## 6. 工具作用域必须收敛

**现象**：ruff 扫进了 `.uv-python`（整个 Python 标准库），报出 1 万多个假错误；后来它又去格式化 Markdown 里的代码块，改掉了设计文档的排版。

**规则**：显式声明 `include`，不要依赖工具的默认边界。噪音会训练人忽略失败集。

## 7. 假设被推翻时，先改文档再改代码

**现象**：项目立项的核心论据是「34% 的合同塞不进上下文」。查官方文档发现上下文是 1M，全部合同都塞得下。

**规则**：前提变了要立刻改 PROJECT/PRD，并留下修正痕迹。否则代码会建立在一个自己都不信的前提上。

## 8. 目标值不能拍脑袋

**现象**：一开始想写「引用准确率 ≥ 85%」。

**规则**：绝对值是拍的，相对基线的提升才是可验证的结论。基线没测出来之前，目标值一律留空，并写明何时填。

## 9. 文档漂移要立刻修

**现象**：README 状态表停在 P0、PROJECT.md 待定项里还挂着已经决定的事。

**规则**：文档与实际不一致时，它就从资产变成了误导下一个 AI 任务的错误上下文。漂移当天修。

## 10. 格式交给工具，不要手对齐

**现象**：手工把注释用空格对齐，`ruff format` 每次都把它压回单空格，产生无意义的 diff。

**规则**：格式由 formatter 决定。手写的对齐在提交前会被推翻，不如一开始就写成工具的输出。

## 11. 任务号说出来，就要同时落成文件

**现象**：原计划 T-011 是交付。M1 后临时把引用修复叫「T-011a」、交付顺延为「T-012」，
但没有建 T-011 的文件。几轮之后，`tasks/` 目录、索引表、对话里的编号三处对不上，
只能回头排查才发现断号。

**判断**：编号是口头状态，文件是持久状态。两者不同步时，漂移发生在最不容易察觉的地方 ——
不在对话里，而在索引表和提交信息里，而这两处恰恰是后来者唯一会看的地方。

**做法**：任务号一旦在回复里说出，同一条回复内就创建任务书文件，
哪怕只有标题、状态行和一行目标。**宁可留一个空壳文件，也不要留一个空号。**

## 12. 分母不同时，准确率不可直接比较

**现象**：18 条冒烟里 anthropic 端点「已判定准确率 90%」看似高于 openai 的 86%，
但前者只对 10 条给出判定、后者对 14 条。分母固定为全部 18 条后，判对数 9 → 12。

**判断**：分母小的口径把不敢判的条目留在分母外，数字天然占优；对齐分母后排序反转。

**做法**：任何准确率必须同时给出分母口径；跨方案比较前先对齐分母。

## 13. 拟合与评估必须分离

**现象**：路由阈值是用 gold 判断哪些条目判错后推给人工 —— 阈值「看过答案」。

**判断**：在同一批数据上既拟合又评估，曲线会显著虚高。

**做法**：CLI 在接口层面禁止 `--curve` 缺省阈值来源；0003 §3 明确写死这条约束。

## 14. 引用「能定位」与「质量高」是两件事

**现象**：M1 首次结果：引用有效率 80.3%、IoU 0.508；修 locator 后有效率 96.0%、IoU 0.615。

**判断**：前者的缺口全部来自空白归一化差异，与模型无关；后者才是模型的引用质量。

**做法**：两个指标分开统计、分开口径说明，不要合并成一个「引用准确率」。

## 15. agent 卡住时看文件产出，不看 token 增长

**现象**：T-008 执行中，token 持续消耗两小时但零文件改动 —— 实为单轮思考撞上输出上限后反复重试。

**判断**：token 消耗衡量「在算」，不衡量「在推进」；活动迹象看起来正常，恰恰掩盖了停滞。

**做法**：判断进度看 `git status` 与产物 mtime，不看活动迹象；必要时中断、清空上下文、拆小任务。

## 16. 同家族模型复查同家族产出，收益有限

**现象**：担心 flash 的实现质量时，想用 glm-5.3 重跑一遍复盘。

**判断**：同家族模型复查同族产出的预期收益很低 —— 训练偏好高度重叠；
更有效的是独立评审（不同模型 / 人）加上可判定的检查（不变量、边界用例、独立复算）。

**做法**：把「谁来验」与「验什么」分开设计，而不是找一个更强的同族模型。
