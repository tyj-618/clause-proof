# 工程心得

每条都来自本项目实际踩过的坑。格式统一为：现象 → 规则。

## 1. 一个契约变更就是一次任务

**现象**：`0002` 从 0.2 升到 0.3 时，文档、实现、测试三处需要同步，手工改到第三处时测试挂了。

**规则**：契约变更牵动多处时，写成一个任务书，交给 AI 一次做完；手工只适合一行 typo 的规模。

## 2. 自述不能作为验收依据

**现象**：实现者报告「make check 全绿、73 个测试通过」，但实际有 3 个失败。

**规则**：任何「已完成」的声明，都要用自己跑的命令复核。审 code 时看 `git diff`，不看对话里的描述。

## 3. 断言格式不等于断言内容

**现象**：错误信息渲染出了错误的实际值，但测试用 `message.startswith("models: X 违反 ")` 断言，格式对，内容错，测试全绿。

**规则**：断言要覆盖「对外可见的每一个部分」。格式和内容分别断言。

## 4. 必填字段比可选字段更能暴露错位

**现象**：两个字段被加错了类（加到了 `CallMeta` 而不是 `RunMeta`），因为它们是必填的，3 个测试立刻变红。

**规则**：契约里不要给默认值。默认值会把错位的字段静默吞掉。

## 5. 生成物不等于该忽略

**现象**：`uv.lock` 是工具生成的，但漏提交它，别人装到的依赖版本就不同，评测数字失去可比性。

**规则**：判据是「别人 clone 后能否重建出**相同**结果」。能重建且与他人无关 → 忽略；能重建但决定版本 → 提交。

## 6. 工具作用域必须收敛

**现象**：ruff 扫进了 `.uv-python`（整个 Python 标准库），报出 1 万多个假错误；后来它又去格式化 Markdown 里的代码块，改掉了设计文档的排版。

**规则**：显式声明 `include`，不要依赖工具的默认边界。噪音会训练人忽略失败集。

## 7. 假设被推翻时，先改文档再改代码

**现象**：项目立项的核心论据是「34% 的合同塞不进上下文」。查官方文档发现上下文是 1M，全部合同都塞得下。

**规则**：前提变了要立刻改 PROJECT/PRD，并留下修正痕迹。否则代码会建立在一个自己都不信的前提上。

## 8. 目标值不能拍脑袋

**现象**：一开始想写「引用准确率 ≥ 85%」。

**规则**：绝对值是拍的，相对基线的提升才是可验证的结论。基线没测出来之前，目标值一律留空，并写明何时填。

## 9. 文档漂移要立刻修

**现象**：README 状态表停在 P0、PROJECT.md 待定项里还挂着已经决定的事。

**规则**：文档与实际不一致时，它就从资产变成了误导下一个 AI 任务的错误上下文。漂移当天修。

## 10. 格式交给工具，不要手对齐

**现象**：手工把注释用空格对齐，`ruff format` 每次都把它压回单空格，产生无意义的 diff。

**规则**：格式由 formatter 决定。手写的对齐在提交前会被推翻，不如一开始就写成工具的输出。
