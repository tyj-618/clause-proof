# 设计文档 0004：错误语义与失败分类

| 项 | 值 |
|---|---|
| 状态 | Draft |
| 版本 | 0.2 |
| 上游 | [设计 0003](0003-interfaces.md)、[PRD-0001](../prd/0001-contract-clause-review.md) |

## 1. 三条原则

1. **单条失败不中断整批。** 3060 条里有一条模型抽风，不该让前面两小时的运行白费。
2. **系统性失败必须快速中断。** 密钥失效、端点不可达这类问题，如果放任跑完，等于烧掉整批预算买一堆相同的错误。
3. **失败必须可分类。** 只统计「失败率」没有信息量；必须能回答「失败在哪里」。

第 1 条与第 2 条冲突，用**熔断**解决。

## 2. 错误分层

| 层 | 时机 | 例子 | 行为 |
|---|---|---|---|
| 配置层 | 启动前 | 缺少模型 key、模型名空、输出目录不可写 | 立即退出，不产生任何记录 |
| 输入层 | 启动前 | 数据集文件缺失、gold span 与原文不符、`split` 值非法 | 立即退出 |
| 单条层 | 运行中 | 模型调用失败、输入超上下文、输出无法解析 | 记为该条失败，**继续** |
| 报告层 | 重算时 | 记录文件损坏、record 与 gold 数量不匹配 | 立即退出 |

## 3. 契约修订：`Judgment` 增加 `parse_ok`

现状有个信息丢失：模型「真的判为不确定」与「我们没能解析出结果」在数据里长得一样（都是 `UNCERTAIN` + 空引用），但它们是**完全不同的问题**——前者要优化提示词，后者要修解析器。

**修订**：`Judgment` 增加一个字段。

```python
@dataclass(frozen=True, slots=True)
class Judgment:
    present: Presence
    quotes: tuple[str, ...]
    confidence: float
    raw_output: str
    parse_ok: bool          # 新增：False 表示解析失败，present 被强制置为 UNCERTAIN
```

新增不变式：

| 类型 | 不变式 |
|---|---|
| `Judgment` | `parse_ok == False` → `present is UNCERTAIN and confidence == 0.0` |

这条改动需要同步到 [0002](0002-data-model.md) §3 与 §7、[0003](0003-interfaces.md) §5 的 `judge` 后置条件。

## 4. 失败分类映射

PRD 7.6 要求失败必须分类。分类不是 `Status`，而是**由 `Status`、`Judgment`、`Spans`、`Gold` 共同推导**出来的结果：

| 分类 | 判定条件 | 依赖字段 | 是否需要 gold |
|---|---|---|---|
| 漏检 | gold 有答案，`present == ABSENT` | judgment, gold | 是 |
| 误检 | gold 无答案，`present == PRESENT` | judgment, gold | 是 |
| 引用定位失败 | `present == PRESENT`，且所有 `Span.valid == False` | spans | 否 |
| 过度自信 | 判定错误，且 `confidence ≥ 0.8` | judgment, gold | 是 |
| 模糊 | `present == UNCERTAIN and parse_ok` | judgment | 否 |
| 解析失败 | `parse_ok == False` | judgment | 否 |
| 超上下文 | `status == CONTEXT_OVERFLOW` | status | 否 |
| 调用失败 | `status == LLM_ERROR` | status | 否 |

**「过度自信」的阈值 0.8 是暂时的**，M1 之后按实际置信度分布调整，并写入变更记录。它衡量的是最危险的一类错误：模型错得干脆利落。

每条记录只归入一个主分类，优先级从下往上：`超上下文` > `调用失败` > `解析失败` > `引用定位失败` > `模糊` > `漏检`/`误检`/`过度自信`。

> 优先级的意义：先回答「这条根本没跑成吗」，再回答「跑成了但对不对」。

## 5. 中断与熔断

**立即中断**（退出码 2）：
- 连续 **5** 条记录为 `CONTEXT_OVERFLOW` 或 `LLM_ERROR`
- 阈值可配置，默认 5

**不中断**：
- 单条 `LLM_ERROR` / `CONTEXT_OVERFLOW`
- 任何 `parse_ok == False`
- 任何判定错误

**熔断的输出**：中断前必须把已完成的记录刷盘，并在 stderr 打印失败原因与已写入条数，保证 `resume` 能接上。

## 6. 退出码

| 码 | 含义 | 触发场景 |
|---|---|---|
| 0 | 成功 | 全部条目完成（含单条失败） |
| 1 | 输入或校验失败 | 数据格式不符、记录与 gold 不匹配、参数非法 |
| 2 | 配置缺失或环境不可用 | 缺 key、端点不可达、目录不可写、熔断 |

`Ctrl-C` 由 shell 约定返回 130，不再单独实现，但要求已写记录完整可读。

## 7. 异常类型

沿用 0003 的约定，只有两种：

| 异常 | 语义 | 谁来捕获 |
|---|---|---|
| `ValueError` | 契约违反：不变式不成立、前置条件不满足 | 不捕获，直接冒泡到顶层 |
| `RuntimeError` | 环境或 IO 失败：模型调用、文件读写 | `runner` 捕获并转为单条失败记录；CLI 捕获并映射退出码 |

不引入自定义异常层级。理由：两个类型已能覆盖全部场景，多一层继承只增加心智负担。

## 8. 错误信息格式

每条错误信息必须包含四要素，缺一不可：

```
<模块>: <字段或参数> 违反 <约束>，期望 <期望值>，实际 <实际值>
```

示例：

```
models: Judgment.confidence 违反 0<=c<=1，期望 [0.0, 1.0]，实际 1.37
```

**禁止出现在错误信息与日志里的内容**：

- API key 或任何凭据（即使是前缀）
- 合同原文超过 80 字符的片段（需要定位时只给 `query_id`）

## 9. 代理环境变量

网络传输遵循 httpx 默认的代理环境变量行为；代理配置错误会表现为构造期失败，而非请求期失败。

这是 NFR-4「无隐式依赖」的已知例外：`HttpxTransport` 的代理行为由运行环境隐式决定，不经过项目配置项。
