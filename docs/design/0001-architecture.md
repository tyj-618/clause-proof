# 设计文档 0001：模块边界与数据流

| 项 | 值 |
|---|---|
| 状态 | Draft |
| 版本 | 0.1 |

## 1. 设计目标

三条约束决定了整个架构的形状：

1. **可测**：核心逻辑必须是纯函数，不 mock 也能单测
2. **防泄漏**：gold 在类型层面不可达，不靠自觉
3. **可审计**：任何结果能追到一次具体运行

## 2. 模块清单

| 模块 | 职责 | 纯度 | 调模型 | 对应需求 |
|---|---|---|---|---|
| `config` | 配置加载、随机种子、路径解析 | IO | 否 | NFR-1, NFR-4 |
| `llm` | 模型调用、缓存、重试、计量 | IO | 是 | FR-6, NFR-2 |
| `dataset` | 读取数据、开发/报告划分、子集抽样 | IO | 否 | FR-1, FR-6 |
| `models` | 数据模型与不变式 | 纯 | 否 | FR-2, FR-3 |
| `judge` | 由查询生成判定 | IO | 是 | FR-2, FR-4 |
| `locate` | 由引用文本定位字符区间 | 纯 | 否 | FR-3 |
| `route` | 阈值选择与路由决策 | 纯 | 否 | FR-5 |
| `calibration` | 校准曲线与 ECE | 纯 | 否 | FR-4, M3 |
| `metrics` | 指标计算、聚合、置信区间 | 纯 | 否 | FR-7, M1–M5 |
| `storage` | JSONL 读写、续跑索引 | IO | 否 | FR-6 |
| `runner` | 批量编排、续跑、落盘 | IO | 否 | FR-6 |
| `cli` | 命令行入口 | IO | 否 | FR-8 |

**纯函数模块占 5/12**，它们承载全部可判定的业务逻辑。IO 模块只做搬运和编排。

## 3. 依赖方向

```
                    ┌─────────┐
                    │  models  │  ← 不依赖任何模块
                    └────┬────┘
                         │ 被所有模块依赖
   ┌─────────┬───────────┼───────────┬─────────┐
   │         │           │           │         │
locate    route    calibration    metrics   storage
   │         │           │           │         │
   └─────────┴───────────┴─────┬─────┴─────────┘
                               │
                            runner ──▶ judge ──▶ llm
                               │
                              cli
```

硬性规则：

- `models` 不导入项目内任何其他模块
- 纯函数模块不导入 `llm`、`storage`、`runner`
- 只有 `judge` 可以直接或间接调用模型

违反这三条，架构就开始腐化。

## 4. 数据流

```
dataset.build_queries(split, spec)
        │
        ├──▶ Query（不含 gold）
        │
      runner
        │
        ├──▶ judge.judge(query)        ──▶ Judgment(present, quotes, confidence)
        │
        ├──▶ locate.locate(quotes, contract_text) ──▶ Span[valid, start, end]
        │
        ├──▶ route.route(judgment, spans, threshold) ──▶ Route
        │
        └──▶ Record ──▶ storage.append(jsonl)

storage.read(jsonl) ──▶ metrics.compute(records, gold) ──▶ Report
                                    ▲
                            gold 只在这一步被加载
```

关键：**gold 只出现在最右侧的 `metrics` 环节**，`Query` 与 `Judgment` 类型里没有它的位置。

## 5. 四条设计原则

**原则一：纯函数优先。**
`locate` / `route` / `calibration` / `metrics` 不读写文件、不调模型。它们可以直接用普通输入测试，不需要 mock 任何东西。项目中所有「答案对错」相关的逻辑都落在这四个模块里。

**原则二：单一模型出口。**
只有 `judge` 会触发模型调用（经由 `llm`）。因此缓存、重试、token 计量、成本统计只需在一处实现，也只需在一处验证。

**原则三：gold 类型隔离。**
`Query` 类型不含 gold 字段；gold 由 `metrics` 从数据源独立加载。这不是纪律，是编译期约束 —— 想泄漏也没有字段可放。

**原则四：数据模型不可变。**
所有跨模块传递的数据模型用不可变结构，并在构造时校验不变式（如置信度必须落在 [0,1]、判定为「无」时引用必须为空）。错误在构造点暴露，而不是流到下游才炸。

## 6. 设计层非目标

- 不做插件系统 / 可替换后端
- 不做多模型并行比较（消融靠多次运行，不靠运行时切换）
- 不做分布式执行
- 不引入编排框架（状态流转由 `runner` 直接实现，逻辑不到 200 行）
- 不做数据库（JSONL 足够，且更易审计）

## 7. 决策记录

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 契约校验方式 | 不可变模型 + 构造时校验不变式 + 单测覆盖；暂不引入静态类型检查 | 把契约质量押在可执行的单测上，比押在类型注解上更实在；"能被类型检查"由运行期不变式保证。静态检查可后续再加，届时只需补注解，不改结构 |
| D2 | 数据模型模块名 | `models`（原拟 `types`） | 避免与标准库 `types` 同名造成误读 |
