# ADR-0002：实现者与评审者分离

- 状态：Accepted（2026-10-26 补记，决策发生于 2026-10-20）
- 日期：2026-10-26
- 决策者：Owner + Tech Lead
- 关联：[CONTRIBUTING](../../CONTRIBUTING.md)、[PROJECT.md](../../PROJECT.md) §11、[CLAUDE.md](../../CLAUDE.md)

## 背景

本项目由「人 + 两个 AI 工具」协作开发（CONTRIBUTING 开篇）。三种角色各有决策域：

| 角色 | 谁 | 决定什么 | 不做什么 |
|---|---|---|---|
| Owner | Tan | 需求取舍、验收、最终决策 | — |
| Tech Lead | DSH | 架构、契约、测试策略、代码评审 | 不写实现代码 |
| Implementer | Claude Code | 按任务书实现、跑测试、报告结果 | 不改契约 |

问题：实现与评审能否由同一个角色（尤其是同一个模型）完成？

## 决策

1. **实现由 Claude Code 完成，评审由 DSH 完成，两者不互换**（CONTRIBUTING「两条铁律」之二）。
2. 这不是流程洁癖：**自回归模型会为自己刚生成的输出辩护，自评存在系统性盲区。**（CONTRIBUTING 铁律原文）评审必须来自一个没有参与生成过程、也不与实现者共享自利倾向的视角。
3. **契约修改权归设计方**：契约是唯一真相源，变更顺序只能是「改契约 → 改测试 → 改实现」；实现方不得擅自改契约——CLAUDE.md 把「修改 docs/design/ 下的契约」列为绝对禁止，有异议只能停下来报告。
4. 落地形态：每个任务书必须含契约片段、验收标准、不变量、禁止事项四件事，并限定允许改动的文件清单；评审按任务书逐条核对，而非通读全部代码。

## 后果

**正面**

- 评审视角与生成视角分离，系统性盲区有第二双眼睛兜底
- 契约先行 + 评审把关，避免「代码写完再倒推文档」
- `main` 受保护（`make check` 通过才合入），评审与门禁互相补位

**负面**

- 评审吞吐受 Tech Lead 一人限制，实现速度快于评审速度时会积压
- 评审者没写过这段代码，存在上下文不对称，深层问题可能漏掉，需靠契约测试兜住下限

**风险**

- 若任务书写得含糊，分离流程会产出「正确实现了错误的要求」——评审质量的上限取决于任务书的质量，分离本身不自动产生质量

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 同模型自写自审 | 自回归模型会为自己刚生成的输出辩护，自评存在系统性盲区（CONTRIBUTING 铁律原文）；等价于没有评审 |
| 只靠人工评审（Owner 一人包揽实现与评审） | Owner 已承担需求取舍与验收，再叠加评审成为瓶颈；且把需求判断与技术判断混在同一个人身上，失去制衡 |
| 只靠测试兜底 | 测试只能证明「实现了任务书」，不能证明「任务书与契约一致」；契约对齐本身需要人审（如 T-001 验收中的「契约矛盾之处要停下来报告」就是机器给不了的判断） |
