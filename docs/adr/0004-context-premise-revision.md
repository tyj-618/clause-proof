# ADR-0004：上下文前提的修正 —— 从「塞不下」到「值不值得塞」

- 状态：Accepted（2026-10-26 补记，原决策发生于 2026-10-19）
- 日期：2026-10-26
- 决策者：Owner + Tech Lead
- 关联：[PROJECT.md](../../PROJECT.md) §2、§4；[PRD-0001](../prd/0001-contract-clause-review.md) §7.4、§8

## 背景

2026-10-19 立项时，对模型能力的判断建立在一个**未经验证的假设**上：

- 假设上下文窗口约 200k tokens
- CUAD 最长合同 338,211 字符，按 3.2–4 字符/token 估算为 85k–106k tokens
- 由此得出：34% 的合同超过 5 万字符，大量合同无法整篇放入上下文

这条推理直接支撑了项目的核心工程价值 ——「分层检索是可行性必需，所以消融实验有天然对照物」。它被写进 `PROJECT.md` §2 与 PRD §7.4，成为整个设计的前提。

事后看，200k 并非来自任何一手资料，而是工具的内置兜底值。

## 触发

2026-10-26，Claude Code 启动时打印了一条警告：

> Model "glm-5.3" isn't recognized · context assumed to be 200k tokens

这句话本身无害，但它暴露了假设的**来源**：200k 是工具的默认值，不是模型的能力。既然工具承认自己「不认识这个模型」，那么「200k」就没有任何证据效力。

## 证据

查阅智谱官方文档后确认（[模型文档](https://docs.bigmodel.cn/cn/guide/models/text/glm-5.3)、[定价页](https://docs.bigmodel.cn/cn/guide/start/pricing)，查询日期 2026-10-26）：

| 项目 | 官方数值 |
|---|---|
| 上下文窗口 | 1M tokens |
| 最大输出 | 128K tokens |
| 输入单价 | ¥8 / 百万 tokens |
| 输出单价 | ¥28 / 百万 tokens |
| 缓存命中 | ¥2 / 百万 tokens |
| 思考功能 | 强制开启，`reasoning_effort` 三档，默认 max |

重算后：

- 最长合同约 85k–106k tokens，约占 1M 的 **10%**
- **510 份合同全部可以整篇容纳**

原假设低估了约 5 倍。

## 决策

1. 撤销「检索是可行性必需」的论证，不再把它当作项目前提
2. 把检索重定位为**成本与精度的权衡**，降级为消融变体（最简实现：段落切分 + top-k，只跑一次对照）
3. 删除「基线可用覆盖率」指标，改为「上下文溢出率（预期 0）」
4. 新增 M6：单条成本与 p95 延迟
5. 关闭 PRD 开放问题 Q1（定价）与 Q2（上下文窗口），记录出处
6. 消融目标改为三列对照：**引用准确率 / 单条成本 / p95 延迟**

**未改动**：span 级引用评测、置信度校准、路由曲线、60/40 按合同划分。这些不依赖上下文大小，前提变了它们依然成立 —— 这本身说明当初的设计把「可验证的评测」和「模型能力假设」分开了，是对的。

## 后果

**正面**

- 在写实现代码之前发现前提错误，避免了 P4 阶段的大规模返工
- 项目主张从「能不能塞」变成「值不值得塞」，更接近真实的工程决策
- 留下一个明确、可证伪的假设：**长上下文下，引用定位精度是否退化**

**负面（如实记录）**

- 如果「整篇塞」在成本可接受时精度更高，检索消融可能被证明毫无价值。届时必须如实报告，而不是调整指标让它好看
- 整篇塞的单条输入成本约为检索方案的 3–4 倍，M1 基线的实际花费高于原估算
- S2 阶段工期存在不确定性：得先跑完基线，才知道检索有没有必要

**风险**

- **1M 上下文不等于有效利用 1M。** 模型在超长输入下的召回可能显著下降，「塞得下」和「用得好」是两件事 —— 而这恰好是消融要测的东西

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留原计划，只把「基线可用覆盖率」改成 100% | 掩盖前提错误。一个恒为 100% 的指标没有信息量，还会让后续读者误以为检索的必要性依旧成立 |
| 放弃检索，专注校准与路由 | 可省 3–4 天，但丢掉唯一涉及长文档的技术深度，且没有对照就无法回答「整篇塞够不够好」 |
| 换一个上下文更小的模型来制造约束 | 人为制造问题。真实工程是在给定模型能力下做成本/精度权衡，不是把工具调弱来论证必要性 |

## 教训

- **把工具的兜底值当作事实，会污染整条设计链。** 一层的假设错误会被下游的指标、架构、里程碑逐级放大
- 关键能力参数必须查一手文档，并在文档中记录出处与查询日期
- 前提改变时要改文档并留下修正痕迹，否则代码会建立在自己都不信的前提上
