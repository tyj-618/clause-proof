## 1. 问题陈述

### 1.1 谁在痛

企业法务专员。合同初筛阶段，他需要逐份确认若干标准条款是否存在、内容是什么，再把结果整理进初筛表交给下游。

### 1.2 现状做法

**假设（未做竞品调研）**：主要依靠 Word / PDF 全文搜索，配合人工通读。

### 1.3 为什么现有做法不够

同一条款在真实合同里有大量同义表述，关键词法需要穷举，且措辞随起草方变化而失效。以「责任上限」为例，至少存在以下写法：

- `cap on liability`
- `limitation of liability`
- `shall not exceed ...`
- `赔偿总额不超过合同总额的 X 倍`

关键词表只能覆盖已见过的写法，**覆盖不了的正是需要人逐字通读的那部分** —— 而这部分恰好是风险最高的长尾。

### 1.4 代价

**假设（待用户访谈验证）**：法务专员约 **50% 的工时**消耗在「定位条款」而非「判断条款」上。

这个假设如果成立，代价有两层：

- **吞吐**：合同批量到达时形成积压
- **质量**：初筛结果依赖个人经验，同一条款不同人给出不同摘录范围

### 1.5 我们要解决的问题

> 初筛阶段的时间主要消耗在「定位与摘录」，而不是「判断」，且定位质量不可控。

注意这个问题陈述的作用：它**排除**了「帮法务做判断」这条路。如果问题是判断质量，方案应该是给建议；但问题是定位耗时，方案就应该优化检索与摘录，并让判断权留在人手里。

## 2. 用户与场景

### 2.1 用户

**初级法务专员** —— 执行初筛的人，不是做最终决策的法务总监。

这个定位带来一个关键约束：初级用户**更依赖清单式工具，也更可能被错误输出误导**。因此「显式标注不确定」不是体验优化，是硬要求。

### 2.2 触发场景

每收到一批合同后，先跑一遍工具，再人工处理。

**假设（待验证）**：一批合同的数量级与发生频率尚未调查。若单批超过 10 份，批量能力是必需的；若长期只有 1–2 份，批量可以降级为可选。

### 2.3 使用流程

1. 导入合同，选择审阅清单
2. 得到按**路由结果**分组的输出：待人工 / 自动通过
3. 只对待人工的条目逐条确认，其余抽查
4. 把结果填进初筛表，交下游

### 2.4 从场景推出的设计约束

第 3 步直接决定了一条功能需求：

> 用户只审批「待定」的内容，所以输出**必须按路由分组**，而不是按合同条款顺序平铺。

这不是界面偏好，是工作流的必然结果 —— 如果按条款顺序输出，用户每次都要自己筛一遍，工具就白做了。

另外两条约束：

- **必须支持批量**（场景是「一批合同」而非单份）
- **不确定必须可见**（用户是初级，无法自行判断哪些结果可信）

### 2.5 用户不需要什么

- 不需要条款解释 —— 他能自己读懂条款，需要的是快速定位
- 不需要法律意见 —— 判断权与责任在法务
- 不需要风险评分 —— 无法客观评测，且会诱导用户盲信

## 3. 范围

### 3.1 覆盖的条款

| # | 条款 | CUAD 原名 | 有答案比例 |
|---|---|---|---|
| 1 | 管辖法律 | `Governing Law` | 86% |
| 2 | 责任上限 | `Cap On Liability` | 54% |
| 3 | 无上限责任 | `Uncapped Liability` | 22% |
| 4 | 转让限制 | `Anti-Assignment` | 73% |
| 5 | 任意终止权 | `Termination For Convenience` | 36% |
| 6 | 续约通知期 | `Notice Period To Terminate Renewal` | 22% |

选择标准是「**存在性判定边界清晰 + 输出可回原文校验**」，不是「法律上最重要」。

### 3.2 判定边界

每条条款分三态：**有 / 没有 / 模糊**。模糊态不硬答，转人工。

| 条款 | 算「有」 | 算「没有」 | 算「模糊」→ 转人工 |
|---|---|---|---|
| Governing Law | 明确写出适用某国家/州/联邦法律 | 全文无管辖法律约定 | 只写「适用相关法律」；约定多个法域但未定优先顺序；管辖法与仲裁地混写 |
| Cap On Liability | 对赔偿总额设明确上限（金额 / 倍数 / 期间费用） | 无任何责任限制表述 | 有上限但同时列出不受上限约束的例外情形 |
| Uncapped Liability | 明确指出某些情形不受责任上限约束（故意、重大过失、保密、IP 侵权等） | 无任何「不受限」表述 | 表述含糊（「在法律允许的最大范围内」） |
| Anti-Assignment | 限制转让合同或其权利（需对方同意 / 绝对禁止 / 限制控制权变更） | 未限制转让 | 只限制部分权利；限制与例外并存；仅限制「控制权变更」而未提合同转让 |
| Termination For Convenience | 一方可在无违约、无需理由的情况下单方终止 | 只能因违约终止，或仅到期终止 | 需提前通知但未说明是否需理由；仅特定情形可终止 |
| Notice Period To Terminate Renewal | 有自动续约条款且给出明确通知期 | 无自动续约，或未约定通知期 | 有自动续约但通知期需推算（「提前一个续约期」） |

**通用规则**：判定为「模糊」时，不要求再给出「有 / 无」；该条目的路由强制为「转人工」。这样评测才能分别衡量「判得对不对」和「是否过度依赖模糊来逃避」。

### 3.3 由数据得出的两条判断

**其一：正负样本高度不均衡。** 六类条款的有答案比例从 22% 到 86%，跨度近 4 倍。这意味着「总体准确率」不是一个有意义的指标 —— 一个永远回答「不存在」的基线在 `Uncapped Liability` 上就能得到 78%。评测必须分类别报告，并用宏平均汇总。

**其二：`Cap On Liability` 与 `Uncapped Liability` 不互斥。** 数据中 111 份含 Uncapped 的合同**全部**同时含 Cap。真实语义是「设有责任上限，但列出若干不受上限约束的例外情形」。因此两者独立判定、可同时为真，输出模型不得假定互斥，也不需要「冲突检测」。

**其三：上下文不是约束。** GLM-5.3 上下文为 1M token，最长合同约 106k token，510 份合同全部可整篇容纳。因此「检索」的价值定位是成本与精度，不是可行性。

## 4. 非目标

| 不做 | 理由 |
|---|---|
| 法律结论、风险评级 | 无法客观评测，且越界；判断权属于法务 |
| 条款解释、风险说明 | 用户是专业法务，自己能读懂；自由文本无法客观评测，会破坏「每条结论都可回原文校验」这一核心性质 |
| 上述 6 类之外的条款 | 范围控制。尤其排除 5 个 License 细分类 —— 它们语义互相重叠，存在性判定会串 |
| PDF 解析与 OCR | 数据源已含纯文本；引入图像链路会带来不可复现 |
| 合同问答（「这份合同有什么风险」） | 与清单式审阅是两种产品形态，混做两头不靠 |
| 中文合同 | 当前数据为英文；跨语言留作未来工作 |
| 前端 UI | 交付形态为 CLI 与 notebook |
| 微调 | 目标是可解释的工程增量，不是模型能力提升 |
| 多 agent 角色扮演 | 对本任务无增益，只增加不确定性 |

九条非目标的作用不是「声明谦虚」，是**挡住后续的扩张**。任何一条被突破，都意味着这个项目已经变形。

## 5. 功能需求

### FR-1 输入展开

**需求**：把数据集展开为可逐条处理的查询单元，每条查询对应「一份合同 × 一类条款」。

**验收标准**：
- [ ] 对 510 份合同 × 6 类条款，产出 3060 条查询
- [ ] 每条查询含唯一标识（合同标题 + 条款名），可用它定位到唯一记录
- [ ] 每条查询含合同全文与条款名，可直接用于构造模型输入
- [ ] gold span 存放在独立字段，**结构上不可能进入模型输入**
- [ ] 任取一条查询，其 gold span 可在全文对应字符区间逐字取回；取不回则该条标记为数据异常并计数

### FR-2 判定与摘录

**需求**：对每条查询给出条款存在性判定，以及**模型声称摘录的原文片段**；判定为「存在」时必须给出至少一段可回原文定位的引用，定位失败则降级为「模糊」。

**验收标准**：
- [ ] 每条查询输出字段：`present`（取值 ∈ {有, 无, 模糊}）、`quotes`（字符串列表）、`confidence`（0–1）
- [ ] `present` = 有 时，`quotes` 非空；`present` = 无 时，`quotes` 为空
- [ ] 一份合同内同类条款出现多处时，`quotes` 需包含全部出现位置，不只报首个
- [ ] 判定为「有」但所有 `quotes` 均定位失败时，必须降级为「模糊」，不得保留「有」+ 空引用
- [ ] 3060 条查询每条都含上述完整字段，无缺失

### FR-3 引用定位与自检

**需求**：对每个 `quote` 在合同全文中定位字符区间，输出区间与有效性标记；该检查不依赖 gold span。

**验收标准**：
- [ ] 每个 `quote` 都被标注 `span_valid ∈ {true, false}`
- [ ] 定位规则：在原文中做精确字符串查找；出现 ≥ 1 次则 `span_valid = true` 并取首次出现作为区间；0 次则 `span_valid = false` 且不产出区间
- [ ] 每个 `quote` 记录出现次数 `occurrences`
- [ ] 定位失败的 `quote` **保留原始文本与标记**，不得直接丢弃（否则失效率无法统计）
- [ ] 可计算「引用有效率」= 有效 `quote` 数 ÷ 全部 `quote` 数
- [ ] 自检可离线复算：仅凭落盘记录即可重算，无需重新调用模型

### FR-4 置信度

**需求**：每条判定附带 0–1 的置信度，且该分数在统计上经过校准 —— 宣称 0.8 的判定，整体正确率应接近 80%。

**验收标准**：
- [ ] 每条查询都有 `confidence ∈ [0, 1]`，包括判定为「无」与「模糊」的条目
- [ ] 可按置信度分桶（10 桶），并输出每桶的样本数与实际准确率
- [ ] 可产出校准曲线与 ECE 数值
- [ ] 校准目标值在成功指标 M3 中定义；本需求只要求「可产出、可复算」

### FR-5 路由

**需求**：依据每条判定的置信度与**按条款类别独立设置**的阈值，决定它是「自动通过」还是「转人工」；并支持以目标人工复核率为约束，反选阈值组合。

**验收标准**：
- [ ] 每条判定输出 `route ∈ {自动通过, 转人工}`
- [ ] 判定为「模糊」的条目一律转人工，不参与阈值比较
- [ ] 阈值按 6 类条款分别设置，共 6 个阈值，互不影响
- [ ] 给定目标复核率 r（默认 20%），能自动选出使实际复核率不超过 r 的阈值组合，并输出实际复核率与目标的偏差
- [ ] 能输出「自动通过准确率」：自动通过条目中判定正确的比例
- [ ] 能输出「复核后整体准确率」：假设人工将转人工条目全部修正，则为 1 − 自动通过且错误的条目数 ÷ 全部条目数
- [ ] 能扫描多个 r 值，产出「人工复核率 – 准确率」曲线

### FR-6 批量运行

**需求**：支持按指定子集批量执行判定，结果逐条落盘为 JSONL，可中断续跑，并记录完整的运行元信息以支持追溯。

**验收标准**：
- [ ] 可指定子集（按合同数量、条款类别、或分层抽样规则）
- [ ] 分层抽样的规则与随机种子一并写入运行记录；同一规格 + 同一种子在两次运行中产出完全相同的查询集合
- [ ] 结果文件为 JSONL：一行一条记录，单行可独立解析，不依赖跨行状态
- [ ] 每条记录至少含：`run_id`、代码版本（commit）、模型名、prompt 指纹、输入 token、输出 token、耗时、原始模型输出、解析后输出、`span_valid`
- [ ] 同一次运行内 `run_id` 一致，且与本次运行的配置指纹绑定
- [ ] 中断后重跑同一子集：已完成的条目不再调用模型，跳过数等于续跑前文件中的记录数
- [ ] 缓存命中单独标注，且不计入成本统计
- [ ] 默认串行执行；若并发度可配置，实际并发度必须记入记录

### FR-7 指标重算

**需求**：仅凭落盘记录与固定随机种子，重算出报告中的全部指标，且结果与报告完全一致。

**验收标准**：
- [ ] 报告中出现的每一个数字，都能由一个「只读 JSONL」的命令重新算出，不需要重新调用模型
- [ ] bootstrap 置信区间的随机种子在运行记录中固定并持久化；同一输入连续重算两次，输出逐位一致
- [ ] 所有比率在输出前统一保留固定小数位（2 位）；**比较在取整之后进行**
- [ ] 指标按条款类别分别输出，并提供宏平均；总体准确率不得作为唯一指标
- [ ] **分母口径固定**：「明确判定准确率」的分母为 `present ∈ {有, 无}` 的条目；「复核后整体准确率」与「模糊率」的分母为全部条目
- [ ] 「模糊」判定不计入明确判定准确率的分母，同时单独输出模糊率
- [ ] 重算结果与已发布报告不一致时，以重算结果为准，并将原报告标记为过期

### FR-8 使用入口

**需求**：提供单一命令行入口，覆盖单合同演示、批量评测、报告重算三类操作。

**验收标准**：
- [ ] 三个子命令：`ask`（单份合同）、`eval`（批量评测）、`report`（指标重算）
- [ ] `ask` 对单份合同的输出包含：判定、原文引用、置信度、路由建议，且整体不超过一屏（约 40 行）
- [ ] 每个子命令的 `--help` 含参数说明与至少一个示例
- [ ] 退出码约定：`0` 成功；`1` 输入或校验失败；`2` 配置缺失
- [ ] 无参数运行时不抛异常，而是打印用法说明

## 7. 成功指标

### 7.1 判定正确的定义

一切指标的基础。gold 侧只有「有答案 / 无答案」两种状态，模型侧有三值：

| gold | 模型输出 | 判定 |
|---|---|---|
| 有 | 有 | 正确 |
| 有 | 无 | 错误（漏检） |
| 无 | 有 | 错误（误检） |
| 无 | 无 | 正确 |
| 任意 | 模糊 | **不计入准确率分母**，单独计入模糊率 |

「gold 有答案」指该「合同 × 条款」在数据集中存在至少一个 gold span。

### 7.2 引用准确率口径

**主口径（引用准确率）**：对每条存在 gold span 的查询，计算预测区间与 gold 区间的最大 IoU；对所有 gold span 取平均，未命中记 0。

**对照口径（宽松）**：预测区间完全落在某个 gold span 之内即记为命中，不计 IoU 大小。

两个口径**同时报告**，M1 与最终版本都要给。

**IoU 阈值 τ**：在 M1 完成后，依据 gold span 的长度分布确定（例如取使基线命中率不出现断崖的取值），确定过程与依据写入变更记录。阈值一经确定，后续所有报告沿用。

**多重 span 的处理**：一条查询可能有多个 gold span。对每个 gold span 独立取最大 IoU 再平均；预测侧多出的区间不额外惩罚，其质量由「引用有效率」单独衡量。

### 7.3 数据集划分

**按合同划分**，不按查询划分 —— 否则同一合同的 6 类条款会同时出现在两个集合中，构成泄漏。

| 集合 | 占比 | 用途 | 允许运行次数 |
|---|---|---|---|
| 开发集 | 60% 合同 | 反复调参、看中间结果、做消融 | 不限 |
| 报告集 | 40% 合同 | 对外报告 | 见下 |

**报告子集**：从报告集中按合同长度分层抽 50 份（短 / 中 / 长各约三分之一），× 6 类 = 300 条查询。该子集一经确定即冻结，作为**所有对外数字的固定评测集**。抽样规则与种子写入运行记录。

**报告子集上的运行次数**：只允许 **2 次** —— 一次是基线（在任何优化之前），一次是最终版本。两次运行都必须如实披露；额外运行视为对报告集的污染，必须重新划定报告子集。

> 说明：50 份合同对应 300 条查询，置信区间会偏宽。是否扩大到 80–100 份，取决于 M1 实测成本，记入第 8 章开放问题。

### 7.4 基线 M1

**定义**：单次模型调用；输入为合同全文、条款名、判定边界说明；不做检索、不重试、不修复引用；置信度为模型自报且未校准。

**适用范围**：全部合同。GLM-5.3 上下文为 1M token，最长合同约 106k token，不会触发上下文溢出。运行中若仍出现溢出，记为 `CONTEXT_OVERFLOW` 单独报告（预期为 0）。

**测量位置：两个子集各跑一次。**

| 子集 | 合同数 | 用途 | 运行方式 |
|---|---|---|---|
| 报告子集 | 50 | **对外对比的唯一基线**，跑完即冻结 | 只跑 1 次 |
| 开发子集 | 50（分层抽样） | 迭代期间参照 | 可反复重跑 |

两个子集上的基线**定义完全一致**，唯一差别是数据来源。开发子集基线可以随代码变化重跑，但对外报告的对比一律使用报告子集上的冻结基线。

**必须报告**：
- 明确判定准确率（分类别 + 宏平均）
- 引用准确率（7.2 的两个口径）
- 引用有效率
- 模糊率
- 上下文溢出率（预期为 0）
- 平均输入 token、输出 token、端到端耗时、单条成本

**目标值**：无。基线定义的是「不做任何优化能到多少」。

**运行条件**：固定模型版本与生成参数；开启缓存；报告子集上运行 1 次，开发子集上可运行 3 次取均值 ± 95% bootstrap 置信区间（种子固定）。

### 7.5 相对指标 M2–M5

| ID | 指标 | 定义 | 对比对象 | 目标值 |
|---|---|---|---|---|
| M2 | 引用准确率提升 | 与基线同口径，IoU 与「完全包含」各报一次 | 报告子集上的冻结基线 | 待 M1 后填 |
| M3 | 校准误差 | 按 confidence 排序后**等频**分 10 桶（每桶样本数相同，桶内不足 30 条时合并相邻桶）；ECE = Σ(nᵢ/N)·\|accᵢ − confᵢ\| | 无（绝对指标） | 待 M1 后填 |
| M4 | 路由价值 | 目标复核率 20% 时并列报告：自动通过准确率、全自动准确率（复核率 0）、复核后整体准确率 | 报告子集上的冻结基线 | 待 M1 后填 |
| M5 | 引用失效率 | 1 − 引用有效率；按条款类别分别报告 | 报告子集上的冻结基线 | 待 M1 后填 |
| M6 | 单条成本与延迟 | 分类别的平均输入/输出 token、单条成本（元）、p95 端到端延迟 | 待 M1 后填 |

**测量位置**：M2–M5 全部在**报告子集**上测量并对外报告，对比对象是 7.4 中冻结的基线。开发子集上的数字可作参考，但必须显式标注「开发集」，且不得出现在摘要或结论中。

**M4 必须给三个数并列。** 只报「复核率 20% 时准确率 92%」没有说服力 —— 读者不知道不加路由是多少，就无法判断这 20% 人工值不值。

**目标值留空是刻意的**：目标相对基线定义，M1 未测量前任何绝对值都是拍脑袋。M1 完成后逐条补填，并在变更记录中登记。

### 7.6 汇总与报告规则

1. **分类别报告 + 宏平均**。总体准确率不得作为唯一指标 —— 六类条款有答案比例从 22% 到 86%，总体数字会被高频类别掩盖。
2. **所有比率带 95% bootstrap 置信区间**，随机种子固定并随运行记录持久化（见 FR-7、NFR-1）。
3. **分母口径**：明确判定准确率的分母为 `present ∈ {有, 无}` 的条目；模糊率与复核后整体准确率的分母为全部条目。
4. **每个数字标注来源 run_id 与集合**（开发集 / 报告子集）。
5. **失败必须有分类**：漏检 / 误检 / 引用定位失败 / 过度自信 / 超上下文。分类之外的不允许出现在报告里。
6. **报告所有子集**，不只报表现好的那部分。
7. **报告子集上的运行次数必须如实披露。** 规定允许 2 次（基线 1 次 + 最终 1 次）；超过 2 次即视为污染，须重新划定报告子集。

## 8. 开放问题

| # | 问题 | 影响 | 何时能解决 |
|---|---|---|---|
| Q3 | 引用准确率的 IoU 阈值 τ 未定 | 直接决定引用准确率的绝对水平，也决定该数字能否与其他项目横向比较。已知 gold span 长度跨度极大（1–2063 字符），固定阈值可能对短条款和长条款不公平 | M1 后，依据 gold span 长度分布确定，并写明选择依据 |
| Q4 | 报告子集合同数量偏少（50 份 / 300 条查询） | 分类别的置信区间会很宽：低频条款（如 Uncapped，22% 有答案）在子集内可能只有 30–40 条正向样本，95% CI 可能达到 ±10% 以上，导致类别间差异不显著 | M1 后按实测成本与 CI 宽度，决定是否扩到 80–100 份 |
| Q5 | 「一批合同」的数量级与发生频率未验证（第 2.2 节的假设） | 若实际每次仅 1–2 份，FR-6 的批量能力与 FR-5 的按路由分组都会从「必需」降为「可选」，输出形态可能从批量报表退回单份清单 | 用户访谈后 |
| Q6 | 引用定位「只取首次出现」（FR-3） | 同一段引用文字在合同中多次出现时，若 gold 对应第 2 处及之后，该条会被误判为错，可能系统性低估引用准确率。低估幅度取决于此类样本占比 | M1 后统计「目标 quote 多次出现」的样本占比，再决定是否改为多处全报 |
