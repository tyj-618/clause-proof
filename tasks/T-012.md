编号接在**当时文件里的最大编号**之后（写这份任务书时为 12–16，

**12. 分母不同时，准确率不可直接比较**
> 18 条冒烟里 anthropic 端点「已判定准确率 90%」看似高于 openai 的 86%，
> 但前者只对 10 条给出判定、后者对 14 条。分母固定为全部 18 条后，判对数 9 → 12。
> 做法：任何准确率必须同时给出分母口径；跨方案比较前先对齐分母。

**13. 拟合与评估必须分离**
> 路由阈值是用 gold 判断哪些条目判错后推给人工 —— 阈值「看过答案」。
> 在同一批数据上既拟合又评估，曲线会显著虚高。
> 做法：CLI 在接口层面禁止 `--curve` 缺省阈值来源；0003 §3 明确写死这条约束。

**14. 引用「能定位」与「质量高」是两件事**
> M1 首次结果：引用有效率 80.3%、IoU 0.508。修 locator 后有效率 96.0%、IoU 0.615。
> 前者的缺口全部来自空白归一化差异，与模型无关；后者才是模型的引用质量。
> 做法：两个指标分开统计、分开口径说明，不要合并成一个「引用准确率」。

**15. agent 卡住时看文件产出，不看 token 增长**
> T-008 执行中，token 持续消耗两小时但零文件改动 —— 实为单轮思考撞上输出上限后反复重试。
> 做法：判断进度看 `git status` 与产物 mtime，不看活动迹象；必要时中断、清空上下文、拆小任务。

**16. 同家族模型复查同家族产出，收益有限**
> 担心 flash 的实现质量时，用 glm-5.3 重跑一遍复盘的预期收益很低 —— 训练偏好高度重叠。
> 更有效的是独立评审（不同模型 / 人）加上可判定的检查（不变量、边界用例、独立复算）。
> 做法：把「谁来验」与「验什么」分开设计，而不是找一个更强的同族模型。

### M4：人工复核率 – 准确率曲线

**不消耗报告集配额、不调用模型** —— 用已有的 300 条记录，按合同哈希拆成拟合组与评估组：

写 `scripts/split_by_contract.py`：

- 读 `results/m1-baseline-dev.spans-v2.jsonl`
- 按 `sha256(contract_id)` 取模把 50 份合同分成两组（约 25 / 25，互斥）
- 分别写出 `results/m1-fit.jsonl`、`results/m1-eval.jsonl`，
  meta 只把 `run_id` 改为 `m1-fit` / `m1-eval`，
  **`split` / `n_contracts` / `seed` / `n_queries` 一律保持原值** ——
  `report` 靠这几个字段重建 gold，改动会导致记录与 gold 错配
- 打印两组各多少条记录、多少份合同

然后：

```bash
uv run clauseproof report --run results/m1-eval.jsonl \
    --thresholds-from results/m1-fit.jsonl \
    --curve --review-rates 0.15,0.3,0.45,0.6,0.75,1.0
```

若某个目标低于评估组的不可约复核率（模糊 + 失败占比），命令会整体失败。
此时降低或去掉该目标重跑，**不要修改代码绕过校验**。

把曲线写进 `docs/experiments/2026-10-28-m1-baseline.md` 的新一节，并说明：

- 拟合组与评估组是**互斥合同**，因此这是留出验证，不是同批拟合
- 样本量（约 150 条）仍然偏小，曲线只作趋势参考
